# Task Center 技术方案选型结论（v1）

## 1. 背景

- 现状：推理与训练由各自 API 直接投递 Celery，编排分散。
- 目标：统一管理生命周期、调度、日志、结果追溯，并支持并行 DAG。
- 约束：旧模块保留，不允许大范围重写执行逻辑。

## 2. 候选方案

### 方案 A：维持现状（模块内直接调 Celery）

- 优点：改动最小
- 缺点：编排与状态分散，定时/自动/重试统一困难

### 方案 B：Task Center 控制平面 + 复用 Celery 执行平面

- 优点：兼容旧链路，成本可控，可渐进演进为 DAG
- 缺点：需要新增编排层和状态聚合逻辑

### 方案 C：引入 Temporal/Prefect/Airflow

- 优点：编排能力强、可观测性好
- 缺点：接入与运维成本高，不适合当前迭代节奏

## 3. 结论

- 选型：**方案 B**
- 理由：
- 最符合“旧模块保留 + 新功能并行”策略
- 可先统一编排，再逐步统一执行和监控
- 风险可控，能快速交付业务价值

## 4. 配套技术决策

- 执行器：继续使用现有 Celery tasks（`inference.batch`、`training.run`）
- 调度：v1 手动触发为主，v1.1 接入 cron 调度
- 状态机：统一扩展为 `blocked/runnable/pending/running/completed/failed/cancelled/timeout`
- 存储：任务中心新表独立；旧表保留并行
- 可观测性：统一 status/log/results API
- 范围收敛：事件链路与 DAG 可视化默认关闭，先保证手动+定时主路径稳定
- 可视化：DAG 编排与运行态可视化作为下一阶段候选能力

## 5. 落地阶段

1. Phase A：模型/API/状态骨架
2. Phase B：真实执行接入 + 调度 + 幂等
3. Phase C：标注来源追溯接入
4. Phase D：灰度评估与替换决策

## 6. 风险与应对

- 调度重入与重复执行：幂等键 + 窗口互斥
- 取消语义不一致：统一取消协议 + timeout 兜底
- 新旧数据口径差异：灰度期双写/对账脚本
